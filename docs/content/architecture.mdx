## Runtime boundaries

The portal UI runs in the browser. Its API, shared management and integration
adapters share the portal application process. The Agent Sandbox controller,
OpenShell gateway and supervisor, and micro VM processes run separately.

Agent Sandbox is required in this view. Kata is optional and selected by default;
it adds micro VM isolation to the workload Pod. Disable it to see a standard Pod.
Omnigent adds its UI, server and runner connection. OpenShell adds protected provisioning and execution;
it replaces the portal’s direct Kubernetes-exec path.

Omnigent UI sign-in, runner registration and working through an existing host
tunnel are separate interactions. Runner registration follows native CLI login;
browser sign-in does not register a micro VM. Choose an interaction to highlight
its path, or select a component for its identity and state ownership details.

## Internet access

The Internet node sits outside the cluster. Follow **Workload connects to Internet**
to see outbound requests and select **Cluster egress** for the policy details.
This box represents platform networking, not another portal deployment.

Direct Agent Sandbox Pods use the operator's cluster networking and policies.
The portal's additional namespace baseline is **off by default**. When enabled,
it denies inbound connections and allows cluster DNS plus public IPv4 TCP/443
unless `publicHttpsEgress` is disabled; selected private/link-local ranges are
excluded. Operators can add explicit rules. An enforcing CNI, routing and any
required NAT remain platform prerequisites.

With OpenShell selected, the trusted supervisor checks relayed requests against
the applied binary/endpoint policy and opens approved external connections.
OpenShell's native outer fence must block direct workload egress. The portal's
optional deny-all baseline adds another policy when enabled; disabling that
baseline does not remove the native fence requirement. Native transport and external connectivity remain
platform prerequisites. The portal does not currently integrate an Envoy egress
service. Kata isolation does not itself change network permissions. See the
[OpenShell v0.1.6 network request path](https://docs.nvidia.com/openshell/v0.1.6/about/architecture#how-a-network-request-travels)
for the native supervisor boundary.

## State and configuration

The profile catalog is deployment-managed configuration. SQLite or PostgreSQL
stores sandbox inventory, intended manifests, namespace grants, operation leases,
controls and announcements. Native runtime state is observed and reconciled
through the selected integration. Persistent storage retains files and login caches; suspension
does not preserve process memory.
